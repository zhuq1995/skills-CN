# 文档共创工作流

该技能提供一个结构化流程，用于引导用户协作创建文档。你要扮演积极的引导者，带用户依次完成三个阶段：收集上下文、结构化与打磨、读者测试。

## 何时提供该工作流

**触发条件：**
- 用户提到写文档：“write a doc”“draft a proposal”“create a spec”“write up”等
- 用户提到具体文档类型：“PRD”“design doc”“decision doc”“RFC”等
- 用户看起来正要开始一项较大的写作任务

**首次建议：**
向用户提出使用结构化共创工作流，并解释三个阶段：

1. **收集上下文**：用户提供相关背景，Claude 提出澄清问题
2. **结构化与打磨**：通过头脑风暴与编辑迭代逐段构建内容
3. **读者测试**：用一个“全新 Claude”（不带上下文）测试文档，在他人阅读前发现盲点

说明这种方式能确保文档在他人阅读时也能工作良好（包括他人把文档粘贴进 Claude 时）。询问用户想走该工作流，还是更偏好自由写作。

如果用户拒绝，就自由写作；如果用户接受，就进入阶段 1。

## 阶段 1：收集上下文

**目标：**缩小“用户知道的”和“Claude 知道的”之间的差距，为后续的高质量引导打基础。

### 初始问题

先询问用户关于文档的元信息：

1. 这是什么类型的文档？（例如：技术规格、决策文档、提案）
2. 主要读者是谁？
3. 希望读者读完产生什么影响/行动？
4. 有需要遵循的模板或固定格式吗？
5. 还有哪些约束或背景需要提前知道？

告知用户可以用速记方式回答，或用任何最省事的方式直接倾倒信息。

**如果用户提供模板或提到文档类型：**
- 询问是否有模板文档可分享
- 如果给出共享文档链接，使用相应集成去获取
- 如果提供文件，直接阅读

**如果用户提到要编辑现有共享文档：**
- 使用相应集成读取当前内容
- 检查是否存在没有 alt-text 的图片
- 如果存在无 alt-text 图片，解释：他人用 Claude 理解文档时 Claude 看不到图片。询问是否需要生成 alt-text；如果需要，请用户把每张图片贴进聊天，以便生成描述性 alt-text

### 信息倾倒

初始问题回答完后，鼓励用户把掌握的上下文尽可能一次性倒出来。可请求的信息包括：
- 项目/问题背景
- 相关团队讨论或共享文档
- 为什么不采用其他备选方案
- 组织背景（团队协作方式、历史事件、政治因素）
- 时间压力或限制
- 技术架构或依赖关系
- 干系人的担忧点

建议用户不用先组织结构——先把信息都倒出来即可。提供多种方式：
- 意识流信息倾倒
- 指向需要阅读的团队频道/线程
- 提供共享文档链接

**如果存在可用集成**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），说明可以用它们直接拉取上下文。

**如果未检测到集成且在 Claude.ai 或 Claude App 中：**建议用户在 Claude 设置里启用 connectors，以便从消息应用和文档存储中直接获取上下文。

告知用户：完成初次信息倾倒后，会继续提出澄清问题。

**在收集上下文过程中：**

- 如果用户提到团队频道或共享文档：
  - 若有集成：告知将立即读取相关内容，然后使用相应集成
  - 若无集成：说明无法访问。建议用户在 Claude 设置中启用 connectors，或直接把相关内容粘贴进来

- 如果用户提到未知的实体/项目：
  - 询问是否要通过已连接工具检索更多信息
  - 在检索前等待用户确认

- 随着用户提供信息，持续跟踪“已学到什么”“还有哪些不清楚”

**提出澄清问题：**

当用户表示初次信息倾倒完成（或已提供大量上下文后），提出澄清问题以确保理解一致：

基于上下文缺口生成 5-10 个编号问题。

告知用户可以速记回答（例如“1：是，2：看 #channel，3：否，因为要向后兼容”），也可以继续给链接、指出要读的频道，或继续信息倾倒；以最省时省力为准。

**退出条件：**
当提问已能体现对上下文的理解——可以直接询问边界情况与权衡，而无需再解释基础信息——即认为上下文足够。

**过渡：**
询问用户此阶段是否还有更多背景要补充，还是可以进入起草文档。

如果用户想补充就继续；准备好后进入阶段 2。

## 阶段 2：结构化与打磨

**目标：**通过头脑风暴、筛选与迭代打磨，按章节逐段构建文档。

**对用户的说明：**
解释将按章节逐段构建文档。对每一章：
1. 先提出澄清问题，确定该章要包含什么
2. 头脑风暴 5-20 个可写点
3. 用户指定保留/删除/合并哪些点
4. 起草该章节
5. 通过“外科式”修改迭代打磨

优先从不确定性最多的章节开始（通常是核心决策/核心方案），再逐步推进其他部分。

**章节顺序：**

如果结构已清晰：询问用户想从哪一章开始。

建议从不确定性最多的章节开始：决策文档通常是核心方案；规格文档通常是技术方案。摘要类章节最好最后写。

如果用户不确定需要哪些章节：根据文档类型与模板，建议 3-5 个合适章节。

询问该结构是否合适，是否需要调整。

**结构确定后：**

创建完整的文档骨架，并为每章放入占位符文本。

**如果可使用 artifacts：**
使用 `create_file` 创建一个 artifact，让 Claude 和用户都有可协作的脚手架。

告知用户将创建包含占位符的初始结构。

创建 artifact：包含所有章节标题与简短占位符，如“[待填写]”“[内容放这里]”。

提供脚手架链接，并说明可以开始逐章填充。

**如果无法使用 artifacts：**
在工作目录创建一个 markdown 文件，并用合适的名字命名（例如 `decision-doc.md`、`technical-spec.md`）。

告知用户将创建包含占位符的初始结构。

创建文件：包含所有章节标题与占位符文本。

确认文件已创建，并说明可以开始逐章填充。

**对每一章：**

### 第 1 步：澄清问题

宣布将开始撰写 [章节名称]。提出 5-10 个澄清问题，明确该章应包含哪些内容：

基于上下文与章节目的生成 5-10 个具体问题。

告知用户可以速记回答，或只指出关键要覆盖的点。

### 第 2 步：头脑风暴

针对 [章节名称]，根据复杂度头脑风暴 5-20 个可写点，重点寻找：
- 可能被遗忘但很重要的已知信息
- 尚未提到的角度或考量

按复杂度生成 5-20 个编号选项。最后询问是否还需要更多选项。

### 第 3 步：筛选

询问哪些点要保留、删除或合并。请求简短理由，以便学习用户偏好并指导后续章节。

给出示例：
- “保留 1、4、7、9”
- “删除 3（与 1 重复）”
- “删除 6（读者已知道）”
- “合并 11 和 12”

**如果用户给的是自由反馈**（例如“都挺好”“大部分可以但……”）而不是编号选择，就提取其偏好并继续推进：解析出要保留/删除/修改的点并应用。

### 第 4 步：缺口检查

根据用户的筛选结果，询问 [章节名称] 是否还缺少重要内容。

### 第 5 步：起草

使用 `str_replace` 把该章节的占位符替换为实际起草内容。

宣布将根据已选内容起草 [章节名称]。

**如果使用 artifacts：**
起草后提供 artifact 链接。

请用户通读并指出要改的地方；强调越具体越利于学习其偏好并改进后续章节。

**如果使用文件（无 artifacts）：**
起草后确认已完成。

告知 [章节名称] 已写入 [文件名]，请用户通读并指出要改的地方；强调越具体越利于后续章节的风格学习。

**给用户的关键指引（首次起草时补充）：**
建议用户不要直接在文档里改，而是指出要改哪里，这样便于学习其写作风格以服务后续章节。例如：“删除 X 这条——Y 已覆盖”“把第三段写得更精炼”。

### 第 6 步：迭代精修

用户给反馈后：
- 用 `str_replace` 做修改（不要整篇重印）
- **若使用 artifacts：**每次修改后提供 artifact 链接
- **若使用文件：**只需确认修改已完成
- 若用户直接改了文档并要求读取：默记其改动并在后续章节中复用（这体现其偏好）

**持续迭代**直到用户对该章节满意为止。

### 质量检查

如果连续 3 次迭代都没有实质变化，询问是否有内容可以删掉而不损失关键信息。

章节完成后，确认 [章节名称] 已完成，并询问是否进入下一章。

**对所有章节重复以上流程。**

### 接近完成

当接近完成（80%+ 章节完成）时，宣布将通读整篇并检查：
- 跨章节的衔接与一致性
- 冗余或矛盾
- 是否存在“水内容”或泛泛的填充句
- 每句话是否都有分量

通读全文并给出反馈。

**当所有章节都起草并精修后：**
宣布所有章节已完成，并说明将再整体复查一遍。

从整体连贯性、流畅度、完整性角度复查。

给出最终建议。

询问是否进入读者测试，还是还想继续微调。

## 阶段 3：读者测试

**目标：**用一个“全新 Claude”（无上下文串味）测试文档，验证其对读者是否真正有效。

**对用户的说明：**
解释现在要做测试，确认文档对读者是否可用，从而抓出盲点——作者觉得理所当然、但读者可能困惑的地方。

### 测试方法

**如果可使用子代理（例如在 Claude Code）：**

无需用户参与，直接执行测试。

### 第 1 步：预测读者问题

宣布将预测读者在理解这份文档时可能会问的问题。

生成 5-10 个读者很可能会实际提出的问题。

### 第 2 步：用子代理测试

宣布将用一个全新的 Claude 实例（不带本对话上下文）测试这些问题。

对每个问题，仅提供“文档内容 + 该问题”来调用子代理。

总结“读者 Claude”对每个问题答对/答错的情况。

### 第 3 步：额外检查

宣布将进行额外检查。

调用子代理检查歧义、错误前提、内部矛盾。

总结发现的问题。

### 第 4 步：汇报并修复

如果发现问题：说明“读者 Claude”在某些点上出现理解困难或误解。

列出具体问题。

说明将修复这些缺口。

回到阶段 2，对有问题的章节进行精修。

---

**如果无法使用子代理（例如 claude.ai 网页端）：**

需要用户手动执行测试。

### 第 1 步：预测读者问题

询问人们在理解此文档时会问哪些问题？他们会在 Claude.ai 里输入什么？

生成 5-10 个读者很可能会实际提出的问题。

### 第 2 步：设置测试

提供测试说明：
1. 打开一个全新的 Claude 对话：https://claude.ai
2. 粘贴或分享文档内容（如果使用支持 connectors 的共享文档平台，就提供链接）
3. 向“读者 Claude”提出上面生成的问题

对每个问题，要求“读者 Claude”给出：
- 答案
- 哪些地方有歧义或不清楚
- 文档默认读者已知哪些知识/背景

检查“读者 Claude”是否答对，是否存在误读。

### 第 3 步：额外检查

也让“读者 Claude”回答：
- “这份文档里哪些地方对读者可能有歧义或不清楚？”
- “这份文档默认读者已具备哪些知识或背景？”
- “这份文档是否存在内部矛盾或不一致？”

### 第 4 步：基于结果迭代

询问“读者 Claude”答错或卡住了哪些地方，并说明将修复这些缺口。

回到阶段 2，对相关章节做针对性精修。

---

### 退出条件（两种方法通用）

当“读者 Claude”能稳定正确回答问题，并且不再暴露新的缺口或歧义时，文档就可以发布。

## 最终复查

当读者测试通过后：
宣布文档已通过“读者 Claude”测试。在结束前：

1. 建议用户自己再通读一遍——他们对文档质量最终负责
2. 建议复核事实、链接与技术细节
3. 请用户确认文档实现了预期影响

询问是否还需要再做一次复查，还是就此结束。

**如果用户需要最终复查，就提供。否则：**
宣布文档完成，并给出几个收尾建议：
- 可以在附录里链接本次对话，让读者了解文档如何形成
- 用附录提供深度信息，避免主文过长
- 真实读者反馈到来后持续更新文档

## 有效引导的提示

**语气：**
- 直接、程序化
- 当理由会影响用户行为时，简要说明即可
- 不要“推销”方法，直接执行

**处理偏离流程：**
- 用户想跳过某阶段：询问是否改为跳过并自由写作
- 用户显得沮丧：承认这比预期耗时，并提出更快推进的方法
- 始终让用户能调整流程

**上下文管理：**
- 全程只要发现上下文缺失就主动追问
- 不要让缺口积累，随出现随解决

**Artifact 管理：**
- 起草完整章节用 `create_file`
- 所有修改用 `str_replace`
- 每次修改后都提供 artifact 链接
- 头脑风暴列表不要用 artifacts，直接在对话里完成

**质量优先于速度：**
- 不要匆忙跳过阶段
- 每次迭代都应带来实质改进
- 目标是让文档对读者真正“可用”
