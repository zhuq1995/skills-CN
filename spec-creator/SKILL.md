# 规范创建器 (Spec Creator)

此技能用于创建结构化的技术规范文档，帮助团队将需求转化为可执行的实现任务。

## 规范结构

每个规范包含三个核心文档：

```
.specs/[规范名称]/
├── requirements.md    # 需求文档 - 定义"做什么"
├── design.md          # 设计文档 - 定义"如何做"
└── tasks.md           # 任务分解 - 定义"谁来做"
```

## 使用流程

### 步骤 1: 收集需求信息

向用户询问以下关键信息：

1. **功能名称**: 规范的主题是什么？
2. **核心目标**: 要解决什么问题或实现什么功能？
3. **目标用户**: 谁会使用这个功能？
4. **关键特性**: 必须包含哪些核心功能？
5. **约束条件**: 有没有技术限制或依赖？

### 步骤 2: 创建需求文档 (requirements.md)

**模板结构**：

```markdown
# 需求文档 - [功能名称]

## 简介

[用 1-2 句话描述功能]

## 术语表

- **Term**: 定义
- **Term**: 定义

## 需求

### 需求 1: [需求标题]

**用户故事**: 作为[角色],我想[目标],以便[价值]。

#### 验收标准

1. WHEN [条件] THEN THE System SHALL [结果]
2. WHEN [条件] THEN THE System SHALL [结果]
```

**编写规则**：
- 每个需求包含用户故事和验收标准
- 验收标准使用 Gherkin 语法 (WHEN...THEN...)
- 保持需求原子性（每个需求只做一件事）
- 至少包含 5 个核心需求

**创建后确认**：文档创建完成后，暂停并让用户确认内容。如有修改意见，调整后再继续步骤3。

### 步骤 3: 创建设计文档 (design.md)

**模板结构**：

```markdown
# 设计文档 - [功能名称]

## 概述

[功能描述和设计目标]

## 架构

[系统架构图或架构说明]

## 组件和接口

### 1. [组件名称]

[组件描述]

#### Props/参数

```typescript
interface xxx { ... }
```

#### Emits/返回

```typescript
interface xxx { ... }
```

## 数据模型

```typescript
interface xxx { ... }
```

## 正确性属性

### 属性 N: [属性名称]

*对于任意*[条件]*,[结果]应该成立*

**验证: 需求 X.X**

## 错误处理

### 错误类型

1. [错误类型]: [描述]

### 处理策略

```javascript
// 处理代码
```
```

**编写规则**：
- 包含系统架构图（使用 ASCII 或 Mermaid）
- 定义清晰的组件接口（Props/Emits）
- 定义数据模型
- 定义正确性属性（用于测试验证）
- 包含错误处理策略

**创建后确认**：文档创建完成后，暂停并让用户确认内容。如有修改意见，调整后再继续步骤4。

### 步骤 4: 创建任务分解 (tasks.md)

**模板结构**：

```markdown
# 实现计划 - [功能名称]

## 概述

[简短描述]

## 任务

- [x] 1. [已完成任务]
  - 具体子任务
  - _需求: X.X_

- [ ] 2. [待完成任务]
  - 子任务
  - _需求: X.X_

- [ ]* 3. [可选任务]
  - 测试任务
  - _需求: X.X_

## 注意事项

- 标记 `*` 的任务为可选测试任务
- 每个任务引用相关需求编号
```

**任务状态标记**：
- `[x]` - 已完成
- `[ ]` - 待完成
- `[*]` - 进行中
- `[ ]*` - 可选测试任务（可跳过以加快 MVP 开发）

**创建后确认**：任务分解创建完成后，询问用户是否需要将测试任务标记为可选（添加 `*` 前缀）。测试任务通常包括：
- 单元测试
- 属性测试
- 集成测试
- E2E 测试

如用户确认，将测试任务标记为 `[ ]*` 并更新任务引用。

## 正确性属性编写指南

正确性属性是形式化验证的基础，格式：

```
### 属性 N: [名称]

*对于任意[条件],[结果]应该成立*

**验证: 需求 X.X**
```

**示例**：
- "对于任意要素添加序列，改善记录应该按时间顺序排列"
- "对于任意有效配置，系统应该正确加载并运行"
- "对于任意状态，保存后恢复应该得到相同状态"

## 验收标准编写指南

使用 Gherkin 语法：

```
WHEN [触发条件] THEN THE System SHALL [预期结果]
```

**示例**：
- WHEN 用户点击保存按钮 THEN THE System SHALL 验证输入并保存数据
- WHEN API请求失败 THEN THE System SHALL 显示错误提示并提供重试选项
- WHEN 用户完成所有要素添加 THEN THE System SHALL 显示知识点总结

## 目录创建位置

规范文档创建在项目根目录的 `.kiro/specs/[规范名称]/` 目录下：

```bash
.kiro/specs/
├── existing-spec-1/
├── existing-spec-2/
└── [新规范名称]/
    ├── requirements.md
    ├── design.md
    └── tasks.md
```
